# pi-arcade-setup

One script that turns a fresh **Raspberry Pi OS Lite (64-bit)** install into a dual-frontend arcade cabinet: **RetroPie** (MAME + a set of common emulator cores) with both classic **EmulationStation** and **ES-DE (EmulationStation Desktop Edition)** available as switchable frontends.

It's a faithful automation of a real, hand-documented build — DSI touchscreen rotation, a source-patched ES-DE with a custom "Restart EmulationStation" quit-menu option, three ES-DE themes, a custom in-frontend "RetroPie Setup" menu, boot splash video, a polkit fix so Reboot/Power Off actually work from a headless kiosk, and a controller-driven brightness/volume hotkey daemon with an in-frontend remapping tool.

The reference hardware is a Raspberry Pi 4 with a **Waveshare 10.1" DSI Touch A** display and a PS4-style **GP2040-CE** controller — the script's defaults match that build exactly. Every hardware-specific value is also a configuration variable, so it works on generic HDMI setups and other controllers too (see [Configuration](#configuration)).

This script has been verified directly against the reference Pi over SSH — every phase's output on disk (display config, ES-DE build + patch, themes, custom RetroPie menu, splash, polkit rule, controller hotkey mapping) was diffed against what `install.sh` actually generates, and a few real discrepancies found in that process were fixed in both places (see [Known limitations](#known-limitations)).

## Quick start

Flash Raspberry Pi OS Lite (64-bit) with Raspberry Pi Imager, set your username/password/Wi-Fi/SSH in the Imager's own customization options, boot the Pi, and SSH in as that user (**not** root). Then run:

```bash
curl -fsSL https://raw.githubusercontent.com/Cr4zySh4rk/pi-arcade-setup/main/install.sh | bash
```

Don't prefix this with `sudo` — the script calls `sudo` itself for the specific commands that need it, the same way the original hand-run build did.

**Before piping a script from the internet into `bash`, read it first.** That's good practice for any curl-into-bash installer, this one included: [install.sh](install.sh).

## What to expect

- Full run time is roughly **1.5–2 hours of actual setup work**, but budget more like **half a day to overnight** if `lr-mame` has to build from source — see [Install time breakdown](#install-time-breakdown) below. It's unattended either way, so this doesn't need babysitting; SSH back in occasionally (or set up a scheduled check) to confirm it's progressing.
- The Pi **reboots itself** at a couple of points (after the base OS update, and after applying display settings if `ENABLE_DSI_DISPLAY=true`). Your SSH session will drop — that's expected. The installer sets up a one-shot `systemd` service that automatically resumes the setup after each reboot, so you don't need to log back in and re-run anything. It removes that service once the whole build is done.
- Progress and errors are logged to `/var/log/pi-arcade-setup.log` on the Pi. If you get disconnected, SSH back in and `tail -f /var/log/pi-arcade-setup.log` to watch progress.
- The script is **safe to re-run**. Every phase is tracked in `/opt/pi-arcade-setup/state`; completed phases are skipped, so if something fails partway (flaky network, a package mirror hiccup) you can just run the same one-liner again.
- By default it reboots into the finished arcade UI when everything is done (`AUTO_REBOOT_AT_END=true`).

### Install time breakdown

Timed end-to-end on the reference Pi (Pi 4, fresh flash) via the installer's own log timestamps:

| Phase | Time | Notes |
|---|---|---|
| Base OS update + display setup | ~15 min | `apt full-upgrade` + one reboot. |
| RetroPie core install (`basic_install`) | ~1h 20min | Once actually running uninterrupted — see caveat below. |
| RetroArch menu rotation patch + rebuild (step 4b) | ~10–20 min | A full `make clean && make` of RetroArch itself, on top of the build `basic_install` already did — needed because the patch changes source that's already been compiled once. Skippable via `APPLY_RETROARCH_MENU_ROTATION_PATCH=false`. |
| Flycast (Dreamcast) build from source (step 4a) | ~10–15 min | No prebuilt aarch64 package exists for this OS release, so this is always a from-source build. Skippable via `ENABLE_DREAMCAST=false`. |
| Emulator/MAME install | **~9 hours** | The dominant cost. This was `lr-mame` compiling from source on-device because no prebuilt binary was available for this platform/OS combo — MAME is a huge codebase and Pi-class hardware is slow at compiling it. If a binary install succeeds instead (depends on your exact OS/board), this phase is minutes, not hours. |
| ES-DE build + everything else (themes, splash, autostart, hotkeys, polkit, custom menu) | ~20 min | |
| **Total** | **~1.5–2 hours of real work, ~9+ hours unattended if MAME builds from source** | |

That reference run's total wall-clock time was actually closer to 17 hours, but roughly 6 of those hours were an early stall/retry loop caused by a passwordless-sudo bug that's since been fixed in this script (see the sudo self-healing logic in `phase_preflight`) — it shouldn't recur on a fresh run. The 9-hour MAME source build is real compute, though, and will happen again on hardware/OS combos without a prebuilt `lr-mame` package.

## What it installs (phase by phase)

1. **Base OS update** — locale (sets `LANG` *and* every `LC_*` category plus `LC_ALL` explicitly, not just `LANG` — `LC_ALL` has the highest precedence, so this is what actually stops a misconfigured SSH client's forwarded locale from producing `bash: warning: setlocale: LC_CTYPE: cannot change locale` over SSH), optional timezone, `apt full-upgrade`, base packages. Also disables the onboard WiFi chip's roaming logic (`brcmfmac roamoff=1`) and NetworkManager's WiFi power-save, working around a known association-failure bug on this hardware — see [Known limitations](#known-limitations). Reboots once for a clean baseline kernel (also needed to load the WiFi fix above).
2. **DSI display setup** *(if `ENABLE_DSI_DISPLAY=true`, the default)* — KMS overlay, kernel cmdline rotation, larger console font for the high-DPI panel. Reboots to activate it.
3. **RetroPie** — clones `RetroPie-Setup` and runs `basic_install` (RetroPie core, RetroArch, classic EmulationStation, standard emulator set).
3a. **GCC 14 CFLAGS compatibility patch** *(if `APPLY_GCC14_CFLAGS_PATCH=true`, the default)* — this OS's default compiler, GCC 14, made calling a C function with no visible declaration (almost always a missing `#include`) a hard error by default, where every GCC before it only warned. That's correct behavior upstream, but it breaks otherwise-fine older C code unchanged for years — including, confirmed live, Flycast's bundled `libzip` dependency (step 4a below) and a second, unrelated spot in `libretro-common`. Rather than chasing every individual instance one at a time, this patches RetroPie-Setup's own compiler-flags setup (`scriptmodules/system.sh`) once, adding `-Wno-error=implicit-function-declaration` to `CFLAGS` project-wide — downgrading the whole class of error back to a warning for anything built from source afterward, not just Flycast. Fail-soft: if a future RetroPie-Setup version changes that line, this is skipped with a warning rather than failing the whole install.
4. **Emulators** — installs `lr-mame` (always) plus the cores listed in `EMULATOR_CORES` (SNES, PS1, PSP, NES, GB/GBC, Genesis, N64, etc. by default).
4a. **Dreamcast (Flycast)** *(if `ENABLE_DREAMCAST=true`, the default)* — installs `lr-flycast` for Dreamcast/Naomi/Atomiswave emulation. Redream, the other well-known Dreamcast emulator, was considered and rejected: its public source only targets x86_64 (the actual Raspberry Pi/"premium" binaries come from a separate closed-source repo), and the official binary is documented to fail to even start on 64-bit Raspberry Pi OS with the modern Mesa v3d KMS driver stack this image uses. Flycast is fully open source with a real ARM64 JIT backend and is the standard way Dreamcast emulation works on a Pi 4 — but there's no prebuilt `lr-flycast` package for aarch64 on this OS release either (confirmed live: "Could not find a binary for lr-flycast"), so this always builds it from source: fetches sources, applies a direct fix to the bundled `libzip`'s missing `#include <unistd.h>` (see step 3a — that patch alone doesn't cover this one, since it's a genuine missing-include bug worth fixing at the source rather than just silencing), then builds, installs, and configures it, and symlinks `flycast_libretro.so` into `~/.config/retroarch/cores/` so ES-DE's already-correct default Dreamcast launch command (`%CORE_RETROARCH%/flycast_libretro.so`) finds it with no extra configuration. You still need to supply your own legally-dumped `dc_boot.bin`/`dc_flash.bin` BIOS files in `~/RetroPie/BIOS/dc` (and, optionally, `naomi.zip`/`awbios.zip` for Naomi/Atomiswave arcade content) before any Dreamcast content will actually run — Sega's firmware isn't and can't be included here. See [Known limitations](#known-limitations).
4b. **RetroArch menu rotation source patch** *(if `APPLY_RETROARCH_MENU_ROTATION_PATCH=true`, the default)* — RetroArch's own menu/quick-menu (RGUI) has no rotation setting at all; it always draws with a hardcoded unrotated projection matrix, a deliberate upstream choice that backfires when "rotation" is actually compensating for a physically-mounted panel like this one. This patches `gfx/drivers/gl2.c` in the source tree `basic_install` (step 3) already fetched and built, then re-runs just RetroPie-Setup's own build+install steps for RetroArch (no full re-clone). The patch does two things: makes the menu draw with the *config's* `video_rotation` instead of skipping rotation entirely, and — since some cores (confirmed: MAME, for ROT90 arcade games like Pac-Man) separately tell RetroArch their own rotation via the libretro API, which would otherwise leak into the menu too — computes the menu's rotation from that config value alone, ignoring whatever any given core requests, so it's correct regardless of which core is currently running. Matched against RetroArch's actual upstream source (verified line-for-line against the version this project's `rp_module_repo` pins); if a future RetroArch version changes this code, the patch step logs a warning and the rebuild is skipped rather than failing the whole install — the menu will just render unrotated, same as stock upstream. See [Known limitations](#known-limitations) for the full investigation.
5. **RetroArch controller autoconfig** — populates RetroArch's *active* autoconfig directory with its full ~440-profile preset library (Xbox, PlayStation, 8BitDo, and hundreds more, matched by USB vendor/product id). Without this, a controller can work fine for menu navigation but do nothing inside actual games — RetroPie only auto-generates an autoconfig profile for a controller you've walked through classic EmulationStation's own input-configuration screen, and ES-DE doesn't do this at all. This closes that gap for any common controller up front.
6. **RetroArch video rotation & aspect fit** — sets `video_allow_rotate = true` and `video_rotation = $RETROARCH_VIDEO_ROTATION` in both `configs/all/retroarch.cfg` and `configs/arcade/retroarch.cfg` (inserted above the arcade config's `#include` line, since RetroArch's config parser only honors the *first* assignment it sees for a key). Also sets `input_quit_gamepad_combo = 4` (Start+Select) here, so Start+Select quits straight back to the frontend — unset by default upstream, confirmed fixed live. This correctly rotates both content (MAME included — MAME's own default `mame_rotation_mode="libretro"` auto-handles vertical-cabinet games with no per-ROM overrides needed) and, separately, fixes scaling: RetroArch computes its aspect-fit viewport using the panel's *native* (pre-rotation) resolution rather than swapping width/height for the post-rotation view, so the default auto-aspect setting produces a narrow, wrongly-scaled image. This phase disables `video_aspect_ratio_auto`/`video_scale_integer` and sets a manually-computed `custom_viewport_*` (expressed in native panel coordinates — see the `PANEL_NATIVE_WIDTH`/`PANEL_NATIVE_HEIGHT` comment in [install.sh](install.sh)) so content ends up centered and correctly filling the real landscape view. Also sets `rgui_aspect_ratio_lock = 0` (None) — its default, INTEGER, made the RGUI Main Menu look too narrow once step 4a fixed its orientation — and `menu_swap_ok_cancel_buttons = true`, so confirm/back in the RetroArch menu follow the physical A/B layout most people expect instead of the Xbox-convention-driven reverse (a genuine, driver-agnostic RetroArch setting confirmed via source, not a cosmetic one, and needing no recompile). See [Known limitations](#known-limitations) for the rotation root cause this replaced (an earlier, incorrect MAME-specific per-ROM mechanism) and for the menu-rotation source patch in step 4a.
7. **File sharing** — ProFTPD, for dropping ROMs onto the Pi over the network.
8. **Disk cleanup** — `apt autoremove`/`clean`.
9. **ES-DE**, built from source (no prebuilt ARM package exists) with `DEINIT_ON_LAUNCH` so it can run directly on the console without a desktop environment.
10. **ES-DE Quit-menu patch** — removes the unreliable "Suspend" option and adds "Restart EmulationStation", by patching ES-DE's C++ source before building it (matched against the real `stable-3.4` source; if a future ES-DE version changes that code, the patch is skipped with a warning rather than failing the whole build).
10a. **ES-DE scraper crash patch** — fixes a genuine upstream ES-DE bug (confirmed by reading the actual source this build compiles): opening Main Menu > Scraper crashes ES-DE outright, with no error message and no log line, whenever any system is tagged `platform=ignore` — which the custom "RetroPie Setup" system (step 15) deliberately is. `GuiScraperMenu`'s constructor loops over every system with an index, skips ignored systems when building the "SCRAPE THESE SYSTEMS" list, but then selects/deselects that list using the *original*, un-adjusted index — running past the end of the list as soon as one system is skipped, and crashing (an unhandled out-of-bounds access) the instant the Scraper screen is built. Patched the same way as the Quit-menu fix above, before building ES-DE. See [Known limitations](#known-limitations).
11. **ES-DE configuration** — first-run default settings, then points it at RetroPie's existing ROM folder and sets the theme/aspect ratio.
12. **Emulator reuse** — symlinks ES-DE to RetroPie's existing RetroArch/PPSSPP install and libretro cores, so nothing is set up twice.
12a. **NES default emulator fix** — ES-DE's built-in `es_systems.xml` lists **Mesen** as the default core for the `nes`/`fds` systems, but RetroPie's binary package repo has no `lr-mesen` (or `lr-fceumm`) build for aarch64 on this OS release — confirmed live, `retropie_packages.sh` silently reports "Could not find a binary" and exits 0. Left alone, every NES ROM fails with `Couldn't find emulator core 'MESEN_LIBRETRO.SO'`, even though `lr-nestopia` (already in `EMULATOR_CORES`) is installed and works. This phase pre-seeds each system's `gamelist.xml` with the `<alternativeEmulator>Nestopia UE</alternativeEmulator>` tag ES-DE's own "Alternative Emulators" menu would otherwise write, so Nestopia UE becomes the default instead — without touching an existing gamelist.xml/override if you've already picked something yourself. **The tag must be a document-level sibling of `<gameList>`, immediately before it — not nested inside `<gameList>`** — confirmed against ES-DE's own `GamelistFileParser.cpp` source (`doc.child("alternativeEmulator")` is read relative to the document root, not the `<gameList>` node), and the exact bug behind this fix not taking effect the first time it was applied. See [Known limitations](#known-limitations).
13. **Themes** — clones three ES-DE themes (`artflix-revisited`, `art-book-next`, `alekfull-nx`) and installs the actual curated per-theme artwork (logos, backgrounds, metadata) for the custom RetroPie-menu system from [`theme-art/`](theme-art) in this repo — pulled directly from the reference build, not generated placeholders.
14. **Frontend autostart/switching** — `autostart.sh` boots into whichever frontend is selected, with the restart-loop and clean-shutdown log detection needed to make Quit/Reboot/Power Off/Restart all behave correctly; a `switch-frontend.sh [esde|classic]` helper and an `esde` relaunch command. Also enables console autologin and installs the `/etc/profile.d/10-retropie.sh` trigger (RetroPie's own optional "autostart" module, which `basic_install` does not enable by itself) so the Pi boots straight into the arcade UI instead of a login prompt. The loop also watches for ES-DE's "Powering off system"/"Rebooting system" log lines and issues the actual `shutdown --poweroff|--reboot now` itself when it sees one — see [Known limitations](#known-limitations) for why.
15. **Custom "RetroPie Setup" system in ES-DE** — a deliberately lean menu (not a reproduction of classic EmulationStation's full config-tools list) inside ES-DE, correctly wired through `openvt`+`TERM=linux` so the tools actually render. In order: **Show IP**, **RetroArch** (opens RetroArch's own RGUI settings menu directly - video, audio, input, per-core options - the same entry classic EmulationStation exposes; RetroPie-Setup's own retropiemenu.sh already has this case handler, this project just re-adds the menu entry pointing at it), **Bluetooth** (pairing wizard, step 24), **Hotkey Config** (step 19), **Audio Player** (step 23), **Bluetooth Player** (step 26), **LED Config** (step 21), **Wifi settings** (step 28, keyboard-gated), **Audio settings** (step 27), **FTP settings** (step 29). Everything else classic EmulationStation's menu used to expose (File Manager, Raspi-Config, Netplay, RetroPie-Setup, Run Command, ES Themes, Splash Screens, Configuration Editor) is intentionally left out to keep the menu short.
16. **Splash screen** — configures the existing RetroPie splash mechanism's rotation, and downloads a custom splash video from `SPLASH_VIDEO_URL` (defaults to the bundled [`splash/retro-splash.mp4`](splash/retro-splash.mp4) in this repo).
17. **Polkit fix** — grants your user passwordless authorization to reboot/power off/suspend, which headless kiosk setups need (`sudo`'s `NOPASSWD` alone isn't enough — this is a separate polkit-layer permission).
18. **Controller hotkey daemon** — holds L3+R3 while pressing Square/X/Triangle/Circle to adjust screen brightness and volume system-wide, regardless of what has input focus.
19. **In-frontend "Hotkey Config" tool** — a full-screen wizard (reachable from the RetroPie Setup menu inside ES-DE, or `sudo python3 ~/scripts/hotkey-remap.py`) to re-capture your controller's button numbers without SSH. Each prompt shows both PlayStation and Xbox naming for the face buttons (e.g. `CROSS / X (Xbox: A)`, `SQUARE (Xbox: X)`) since the physical button a controller reports as "X" differs between the two conventions.
20. **LED strip daemon** — drives an addressable WS2812B strip via `rpi_ws281x` (hardware DMA-timed output, the same class of approach [WLED](https://kno.wled.ge) itself uses on ESP32 via its RMT peripheral, rather than CPU bit-banging) with twelve effects (solid, flash, breathe, wave, rainbow, chase, theater_chase, bounce, color_wipe, sparkle, confetti, fire), reading color/brightness/speed/LED-count live from a config file so changes from the LED Config tool apply instantly with no restart.
21. **In-frontend "LED Config" tool** — a full-screen wizard (reachable from the RetroPie Setup menu inside ES-DE, or `sudo python3 ~/scripts/led-config.py`) to set the strip's effect, color, brightness, animation speed, and live LED count — fully navigable by controller (left stick to move/adjust, X/Cross to confirm, Circle/B to exit) as well as keyboard.
22. **Aux audio output pin** — this build has no HDMI-audio-capable display, so it pins PipeWire/WirePlumber's default output to the 3.5mm jack (found by matching the bcm2835 "mailbox" ALSA card, not a hardcoded id) via `wpctl set-default`, which WirePlumber remembers by node name across reboots — so this survives even if a monitor with HDMI audio gets plugged in later.
23. **"Audio Player" tool** — an Apple-Music-styled full-screen MP3/FLAC/OGG/WAV player (`~/scripts/music-player.py`, via `python-vlc`) for files in `MUSIC_DIR`, reading ID3/FLAC/OGG tags with `mutagen` when available. Shows a "Now Playing" card (title, artist/album, progress bar, play/pause state) above a scrollable library list, and is fully controller-navigable: up/down browses the library, left/right adjusts volume, confirm plays the highlighted track or toggles play/pause, back exits (stopping playback).
24. **"Bluetooth" pairing wizard** — replaces RetroPie's default Bluetooth tool with a controller-navigable one (`sudo python3 ~/scripts/bt-controller-pair.py`) built directly on BlueZ's D-Bus API rather than parsing `bluetoothctl` text output. Scans continuously, lists nearby devices live, and pairs/trusts/connects the selected one with a single button press — pairing confirmation itself is handled unattended by the `bt-agent` service (step 25), so there's no PIN entry. Meant mainly for wireless controllers, but works for any discoverable device.
25. **Bluetooth speaker daemon** — turns the Pi into an A2DP sink advertised as `BT_SPEAKER_NAME` (default `RetroPieArcade`), using **BlueALSA** (`bluez-alsa-utils`: `bluealsa` + `bluealsa-aplay`) rather than PipeWire/WirePlumber's own `bluez5` SPA monitor. That was the original design (this image already runs PipeWire for everything else), but it turned out unreliable specifically for A2DP on the reference Pi's onboard Bluetooth chip — media endpoints got registered/unregistered per connection attempt instead of staying up, and profile connections consistently failed as unavailable even once a phone was paired, confirmed via low-level `btmon` HCI captures across many repeated attempts. PipeWire's own Bluetooth monitor is disabled via a WirePlumber user-config override (`~/.config/wireplumber/wireplumber.conf.d/51-disable-bluez-monitor.conf`) so the two don't both try to register the same profile with `bluetoothd`; `bluealsa` registers the Audio Sink profile once, persistently, at its own startup (restricted to sink-only via a systemd override — a stock install also advertises source), and `bluealsa-aplay` decodes the stream into the Pi's normal "default" ALSA device, which still resolves through PipeWire (see step 22), so it comes out the same pinned aux/HDMI output as everything else. Four systemd services back it: `bt-agent` (this project's own headless BlueZ pairing agent, `~/scripts/bt-pairing-agent.py`, implementing `org.bluez.Agent1` directly over D-Bus — auto-accepts every pairing request with no PIN prompt, advertised with `DisplayYesNo` capability rather than `NoInputNoOutput` specifically because some phones request MITM-protected "Dedicated Bonding" during pairing, which BlueZ auto-rejects under `NoInputNoOutput` before the agent is ever consulted), `bt-power-on` (powers the adapter on at boot only — it is deliberately *not* discoverable/pairable at boot; see the "Bluetooth Player" tool below for when it is), `bluealsa`/`bluealsa-aplay` (the A2DP backend itself), and `bt-nowplaying-daemon` (polls BlueZ's `MediaPlayer1`/`Device1` D-Bus objects for AVRCP now-playing metadata, auto-trusts newly paired devices, proactively reconnects a paired phone's A2DP link while the "Bluetooth Player" screen is open, explicitly disconnects it the instant that screen closes, and executes play/pause/next/previous commands). The advertised name comes from `/etc/machine-info`'s `PRETTY_HOSTNAME` — BlueZ's `hostname` plugin overrides `main.conf`'s `Name=` with that value by default, so that's the file that actually controls what phones see. `loginctl enable-linger` keeps the `pi` user's PipeWire session (which `bluealsa-aplay` plays into) running even without an active console session. Only one device is ever treated as the active audio source: `bt-nowplaying-daemon` tracks whichever device was last actually seen connected and, if it drops its A2DP link, only ever tries to reconnect *that specific device* — not every other paired device — and only when nothing else is currently connected. This scoping is what stops a stale device from racing back in: disconnecting device A and connecting device B used to be able to leave the daemon trying to reconnect the just-disconnected A (a paired device with no scoping to say otherwise) right as B was connecting from its own side, contending for the single A2DP link the onboard radio can hold and leaving B unable to play until you forgot/re-paired it. If two devices somehow still end up connected at once, it disconnects whichever one it already knew about and keeps the new one — a stale device can't linger and get shown or fought over instead of whatever you're actually connecting right now. `bluealsa-aplay` is also tuned via a systemd override (`--single-audio --pcm-buffer-time=1000000 --pcm-period-time=100000`, up from its 500ms default): it opens a fresh connection to the ALSA device for every new Bluetooth audio stream, which some sources (confirmed live with a MacBook) do again at every track change, not just once at connection time — the larger buffer gives enough headroom to ride through that renegotiation without an audible chop, at the cost of a bit more latency, an easy trade for background music.
26. **"Bluetooth Player" tool** — a car-infotainment-style now-playing screen (`~/scripts/bt-nowplaying.py`, on-screen header reads "Bluetooth Player") for whatever's streaming from a phone connected to the speaker above: track title (marquee-scrolls if long), artist/album, progress bar, and connection status. Controller-navigable: left/right skips to the previous/next track, up/down adjusts the Pi's own output volume, confirm toggles play/pause, back exits — closing this tool does not stop playback initiated elsewhere, since the audio path itself is handled entirely by the background daemon. The Pi only behaves as a Bluetooth *audio* device — discoverable/pairable to new phones, and actively holding/reconnecting a paired phone's A2DP link — while this screen is open; closing it explicitly disconnects any connected phone and turns discoverable/pairable back off, so game/UI audio stays on the Pi's own output and a paired Bluetooth game controller isn't sharing the single Bluetooth radio with an idle audio link the rest of the time. This is a completely separate BlueZ profile (A2DP) from controller pairing (HID, handled by the kernel) — none of this affects a paired game controller. To pair a phone for the first time: open this tool first, then pair from the phone's Bluetooth settings.
27. **"Audio settings" tool** — a controller-navigable output/mixer front end (`~/scripts/audio-settings.py`) for `wpctl`: cycle the default output between the aux jack and any HDMI port, and adjust master volume/mute.
28. **"Wifi settings" tool** — WiFi setup needs a real keyboard (for the SSID/password), so this (`~/scripts/wifi-settings.py`) asks first — "Do you have a keyboard plugged in?", controller-selectable — rather than silently dropping a controller-only user into a screen they can't use. Answering yes launches `nmtui` (this OS image's WiFi stack is NetworkManager, not `wpa_supplicant`).
29. **"FTP settings" tool** — a two-row, independently switchable on/off screen (`~/scripts/ftp-settings.py`) for both file-transfer methods this image exposes: **FTP** (the ProFTPD server installed in step 7, port 21, wrapping `systemctl enable/disable --now proftpd`) and **SFTP** (file transfer over the SSH connection you already use to manage the Pi, port 22). Up/down picks a row, confirm toggles it. SFTP's toggle does *not* touch the `ssh` service itself — sshd stays up the whole time, since that's this project's only remote shell/management path — it only comments out or restores the `Subsystem sftp ...` line in `/etc/ssh/sshd_config` and reloads (not restarts) sshd, which re-reads config without dropping any existing session. Both rows show their connection address (`ftp://`/`sftp://`) when on.
30. **CPU/GPU overclock** *(if `ENABLE_OVERCLOCK=true`; **on by default**, see [Known limitations](#known-limitations) for the rotation debugging history around this setting; runs early, right after preflight)* — on a Raspberry Pi 4, bumps the CPU to `OC_ARM_FREQ` (2000MHz) and the GPU/VideoCore core clock to `OC_GPU_FREQ` (675MHz), with the extra `over_voltage` (6, i.e. +0.15V) both need for stability at those clocks. Written as a `[pi4]`-scoped block in `/boot/firmware/config.txt` (a real config.txt conditional filter, not just a comment) so it's a no-op if this script's ever run on different Raspberry Pi hardware, and stripped/reapplied by marker comments on re-run so changing `OC_*` and re-running the installer doesn't leave stale duplicate values behind. Takes effect on the next reboot, which this phase triggers itself.

## Configuration

Everything is an environment variable with a sensible default, so `curl ... | bash` reproduces the reference build with no input needed. Override any of them by exporting the variable first, e.g.:

```bash
ENABLE_DSI_DISPLAY=false ENABLE_CONTROLLER_HOTKEYS=false \
  curl -fsSL https://raw.githubusercontent.com/Cr4zySh4rk/pi-arcade-setup/main/install.sh | bash
```

| Variable | Default | Purpose |
|---|---|---|
| `PI_USER` / `PI_HOME` | current user / `$HOME` | Account the arcade UI runs as. |
| `LOCALE` | `en_US.UTF-8` | System locale. |

## After install

- **Copy ROMs** into `~/RetroPie/roms/<system>/` (e.g. `arcade`, `snes`, `psx`, `psp`) over the network via FTP (ProFTPD, port 21, jailed to your home directory) or SFTP (over SSH, port 22) — both switchable independently from the "FTP settings" tool — then rescan from the frontend or reboot.
- **Add Dreamcast BIOS files**: Flycast (installed by step 4a) needs `dc_boot.bin` and `dc_flash.bin` — dumped from your own Dreamcast console — copied into `~/RetroPie/BIOS/dc/` (same FTP/SFTP path as ROMs above). Without both files present, Dreamcast content won't boot. These are copyrighted Sega firmware, so this project can't include or download them for you; for Naomi/Atomiswave arcade content via Flycast, also add `naomi.zip`/`awbios.zip` to the same folder.
- **Switch frontends**: `~/switch-frontend.sh esde` or `~/switch-frontend.sh classic` (takes effect on next boot/restart).
- **Relaunch ES-DE** without rebooting after a deliberate Quit: run `esde`.
- **Remap controller hotkeys**: RetroPie Setup → *Hotkey Config* inside ES-DE, or `sudo python3 ~/scripts/hotkey-remap.py` over SSH.
- **Add music**: drop MP3/FLAC/OGG/WAV files into `~/RetroPie/Music/` (or wherever `MUSIC_DIR` points), then open *Audio Player*.
- **Pair a controller**: RetroPie Setup → *Bluetooth*, put the controller in pairing mode, select it from the live-scanning list, and press confirm — no PIN prompt.
- **Stream from a phone**: open *Bluetooth Player* in the RetroPie menu first — this is what makes the Pi discoverable/pairable and actively hold an A2DP link, only while it's open — then pair the phone to `BT_SPEAKER_NAME` (`RetroPieArcade` by default) from the phone's Bluetooth settings (no PIN prompt on either side) and play something; the screen shows the track and lets you skip/pause from the controller. Closing the screen disconnects the phone and turns the Pi back into a plain Bluetooth host — so a paired game controller isn't sharing the radio with an idle audio link — and reopening the screen automatically reconnects an already-paired phone.
- **Logs**: `/var/log/pi-arcade-setup.log` (installer), `~/ES-DE/logs/es_log.txt` (ES-DE), `/var/log/controller-hotkeys.log` (hotkey daemon), `/var/log/bt-nowplaying-daemon.log` (Bluetooth AVRCP daemon).
- **Controller works in menus but not in-game?** This is almost always a missing RetroArch autoconfig profile, not a broken controller — the installer pre-populates ~440 common profiles (step 5 above), but a controller RetroArch has never seen the exact USB identity of won't have one. Confirm with `grep -i autoconf <(XDG_RUNTIME_DIR=/run/user/$(id -u) timeout 5 /opt/retropie/emulators/retroarch/bin/retroarch --verbose --menu 2>&1)` over SSH — it logs a line like `[Autoconf]: Xbox 360 Controller configured in port 1` on success, or silence if nothing matched. DIY/open-source controllers (e.g. GP2040-CE-based sticks) can also present a *different* USB vendor/product ID per input mode (PS4/PS5/XInput/etc.), each needing its own match — switching modes is effectively switching to what RetroArch sees as a different controller.

## Known limitations

- **In-game RetroArch content rotation is now fixed — not by disabling the CPU/GPU overclock, despite an earlier pass through this project blaming it.** An earlier version of this project shipped a large `phase_mame_rotation_autofix` mechanism (auto-detecting vertical-cabinet MAME ROMs via a `mame -listxml` dump and forcibly setting `mame_rotation_mode` per-ROM) plus a live L3+R3+Dpad in-game hotkey, believing MAME-specific handling was needed. It wasn't. Diffing a full config snapshot (retroarch.cfg, config.txt, kernel/RetroArch versions, DRM plane capabilities) against a known-good reference SD card - otherwise identical - pointed at the GPU overclock (`gpu_freq` above stock 500MHz) as the cause, since disabling it alongside several other changes coincided with rotation working again. That specific claim did not hold up: once the real fixes below (the aspect/viewport coordinate-space bug and the RGUI/menu source patch) were in place, re-enabling the overclock did not reproduce any rotation problem - confirmed live, with `ENABLE_OVERCLOCK` back to `true` by default. MAME's own default `mame_rotation_mode="libretro"` (auto, per-ROM) already handles vertical-cabinet games correctly - forcing `tate-ror` on top of that, as the old mechanism did, actively double-rotated/stretched those games regardless of the overclock. The old per-ROM mechanism and hotkey have been removed entirely.
- **Fixing rotation exposed a separate scaling bug, also now fixed.** RetroArch computes its aspect-ratio-fit viewport using the panel's *native* (pre-rotation, portrait) resolution rather than the rotated (landscape) one, and does not swap width/height for this calculation even with `video_rotation` active - confirmed live: the default auto-aspect setting produced a correctly-proportioned image sized for a *portrait* screen, then rotated into the landscape one, coming out narrow and tall. `video_scale_integer` (whole-pixel-multiple-only scaling) compounded this by leaving most of the screen unfilled even after that was corrected - this key isn't set by RetroPie-Setup at all (confirmed absent from the reference SD card), so it must have been toggled on separately at some point. Step 6 now disables both `video_aspect_ratio_auto` and `video_scale_integer`, and sets a manually-computed `custom_viewport_*` - expressed in *native* panel coordinates, since that's the coordinate space RetroArch actually applies these values in, then rotates the whole result - so the final displayed image comes out centered and correctly filling the real landscape view.
- **The RetroArch menu itself (RGUI, opened via the Home button in-game or the restored "RetroArch" RetroPie-menu entry) was rotated 90° with no way to fix it via configuration — this is now fixed with a source patch, applied automatically (step 4a).** Confirmed by searching the compiled RetroArch binary directly for every rotation- and menu-related symbol it exports (`video_rotation`, `screen_orientation`, `rgui_aspect_ratio`/`rgui_aspect_ratio_lock`, every `menu_*`/`rgui_*` symbol) — only aspect-ratio controls exist for the menu, no rotation one, confirmed identically present on the known-good reference SD card too (a pre-existing RetroArch limitation on this driver stack, not a regression from anything in this project). Investigating RetroArch's actual upstream source (`gfx/drivers/gl2.c`) found the real cause: `gl2_draw_texture()`, the function that draws the menu's rendered framebuffer to the screen, hardcodes the *unrotated* projection matrix (`mvp_no_rot`) instead of the rotated one every content frame uses — a deliberate upstream choice (keep the menu upright even when content is rotated) that doesn't hold when "rotation" is compensating for a physically mounted panel. Patching that one call fixed the standalone Main Menu and the in-game Quick Menu for non-MAME content (confirmed: SNES) immediately, but the in-game Quick Menu was still wrong specifically during MAME sessions (confirmed: Pac-Man) — a second, separate bug: MAME calls the libretro `RETRO_ENVIRONMENT_SET_ROTATION` callback for ROT90 arcade games, which overwrites RetroArch's internal rotation value with just MAME's own raw request instead of combining it with this project's panel-rotation config (`video_driver_set_rotation()` passes the core's value straight through, per `runloop.c`/`gfx/video_driver.c`) — harmless for game content, since MAME separately pre-rotates its own frame buffer to compensate, but wrong for the menu once it started sharing that same value. The patch actually applied builds the menu's rotation matrix from the config's `video_rotation` alone, ignoring whatever any core requests, which fixed Pac-Man's Quick Menu too without touching Mortal Kombat's (already-correct) one. See the `APPLY_RETROARCH_MENU_ROTATION_PATCH` comment in [install.sh](install.sh) for the exact patch.
- **MAME ROM files must be named for and dumped against MAME 0.289** (the version `rp_module_repo` pins for `lr-mame`) — an older ROM set will not just "work with a warning," it can fail outright in two different ways. First, the zip's *filename* (without extension) has to exactly match one of MAME's own internal machine short names — confirmed live with a "Street Fighter" ROM named `sf1.zip`: MAME rejected it with `Unknown system 'sf1'` and suggested the real name, `sf` (MAME has no machine called `sf1` at all; the actual short names for this game are `sf`/`sfj`/`sfw`/`sfp`/etc. depending on region). Renaming to match the correct short name is sometimes enough on its own, but second — and this is the one a rename can't fix — MAME's exact *set* of required files for a given machine can change across major version eras as its driver gets reverse-engineered further (files split, renamed, or newly required as understanding of the real arcade PCB improves). Confirmed live: after renaming to `sf.zip`, MAME correctly identified the game but then failed with `Fatal error: Required files are missing, the machine cannot be run` — the zip (originally dumped for MAME 0.139u1, from 2013) was simply missing six files (`sfd-19.2a`, `sfd-22.2c`, `sfd-20.3a`, `sfd-23.3c`, `sfd-21.4a`, `sfd-24.4c`) that 0.289 now requires for that machine. If a ROM you've added launches straight back to the frontend with no error visible in ES-DE, run it directly over SSH with `retroarch -L /opt/retropie/libretrocores/lr-mame/mamearcade_libretro.so --config /opt/retropie/configs/arcade/retroarch.cfg --verbose <path-to-rom>` — MAME logs an exact reason (unknown system, missing files, bad checksum, etc.) that ES-DE's own UI never surfaces.
- **NES ROMs (e.g. Super Mario Bros.) fail with `Couldn't find emulator core 'MESEN_LIBRETRO.SO'`, even on a fresh install with no config changes.** ES-DE's built-in `es_systems.xml` lists **Mesen** as the first (default) emulator command for the `nes`/`fds` systems, but RetroPie's binary package repo has no `lr-mesen` build for aarch64 on this Debian release (nor, it turns out, `lr-fceumm` either) — confirmed live: `sudo ./retropie_packages.sh lr-mesen _binary_` (and `lr-fceumm`) both exit 0 with just `Errors: Could not find a binary for ...`, no `.so` ever lands, and `phase_emulators_install`'s existing "didn't install" check only warns, it doesn't fail the run. `lr-nestopia` (already in `EMULATOR_CORES` by default) does have a working aarch64 binary and installs fine, but ES-DE still tries Mesen first regardless. Fixed by pre-seeding the `nes`/`fds` `gamelist.xml` files with the `<alternativeEmulator>Nestopia UE</alternativeEmulator>` override ES-DE's own UI would otherwise write (step 12a). The first attempt at this fix nested the tag *inside* `<gameList>`, which parses without error but is silently never read — ES-DE's `GamelistFileParser.cpp` looks it up via `doc.child("alternativeEmulator")`, i.e. as a document-level sibling of `<gameList>`, immediately before it, not a child of it (confirmed by reading the actual source this build compiles, at `~/emulationstation-de/es-app/src/GamelistFileParser.cpp` on the Pi) — so the ROM kept launching with the missing default core even after a reboot. With the tag correctly placed outside `<gameList>`, it takes effect on ES-DE's next parse of that gamelist (a restart of ES-DE, or a reboot). If RetroPie ever ships an aarch64 `lr-mesen`/`lr-fceumm` binary for this OS release, either core can be installed and set as the default in the same way, but Nestopia UE is a fully capable NES core in its own right.
- **The onboard WiFi could fail to associate with a real, correctly-configured, in-range network with "the Wi-Fi network could not be found," even though it's right there** — a known, still-unresolved upstream firmware bug on the Cypress/Infineon BCM4345/6 chip this Pi uses, not a bug in this project's networking setup. Confirmed live: two different real home networks both failed on every single connection attempt via the "WiFi settings" tool, each ending in NetworkManager's generic "activation failed: the Wi-Fi network could not be found" — despite both being confirmed visible with a strong signal (-47 to -49 dBm) via a raw `iw scan`, and both having the correct password already stored in the connection profile. The actual wpa_supplicant log told the real story: `CTRL-EVENT-ASSOC-REJECT bssid=00:00:00:00:00:00 status_code=16` on every attempt — the all-zero BSSID means this rejection is generated locally by the driver/firmware itself, not a real frame received from the router. Ruled out live, in this order, before finding the real cause: WiFi power-save (disabled, no change), Bluetooth contention for the shared antenna (powered off entirely, no change), a stale NetworkManager scan cache (a fresh, unrelated `iw scan` reliably found both networks throughout). This exact symptom is [widely reported](https://github.com/RPi-Distro/firmware-nonfree/issues/38) on this chip with no official fix. The community's most consistently-reported workaround — disabling the driver's own roaming logic via `options brcmfmac roamoff=1` in `/etc/modprobe.d/brcmfmac.conf` (harmless here regardless, since a stationary kiosk never roams between APs) — resolved it immediately on the reference Pi: failed on every attempt before a reboot with this in place, connected on the very first attempt after. Applied automatically in step 1; if you hit this on different hardware where it doesn't help, the `iw scan`-vs-`nmcli`/journalctl comparison above is the fastest way to confirm you're looking at the same bug before trying anything else.
- **N64 (`mupen64plus_next`) is flaky to build** upstream — the script installs it best-effort and continues without failing the whole run if it doesn't compile. On the reference Pi this core never ended up installed, matching the original build log's note.
- **The ES-DE Quit-menu source patch is matched against `stable-3.4`.** It's applied as an exact text match against the real upstream source (verified against the actual `stable-3.4` files at build time, and against the compiled binary on the reference Pi via `strings` — the "RESTART EMULATIONSTATION" menu text is present), and fails soft — if you build a different `ESDE_BRANCH` and the surrounding code has changed, the patch step logs a warning and ES-DE still builds, just without that menu entry.
- **Controller button numbers are hardware-specific** and can drift even for the *same* controller (reconnects, firmware mode changes). The defaults shipped here are whatever the reference Pi's controller is actually mapped to right now, captured live via the remap tool — re-capture for your own controller with the in-frontend "Hotkey Config" tool after install regardless.
- **The RetroPie-menu "Splash Screens" tool can silently drop the custom rotation flag.** `splashscreen.cfg`'s `--transform-type=$SPLASH_TRANSFORM_TYPE` is a hand-added option outside what that GUI tool manages: using it to pick/enable a splash video appears to regenerate the file and lose the custom flag (this happened on the reference Pi and was fixed by hand). If your splash video looks unrotated after using that menu, re-run `phase_splash_setup` logic manually or just re-apply the `CMD_OPTS` line shown in [install.sh](install.sh).
- **`SPLASH_TRANSFORM_TYPE` only reliably rotates image splashes, not video ones.** Confirmed by running `vlc -vv` on the reference Pi: h264 video gets hardware-decoded straight to a DRM_PRIME buffer that VLC's `transform` video filter can't process (`Unsupported pixel size 0 (chroma DPV0)`), so VLC logs `removing all filters` and plays the video completely unrotated, regardless of `--transform-type`. This is why the bundled [`splash/retro-splash.mp4`](splash/retro-splash.mp4) has its correct orientation baked directly into the file instead (`ffmpeg -vf transpose=2`, a 90° counter-clockwise/270° clockwise correction for the source clip, verified visually on the reference Pi's actual panel). If you supply your own `SPLASH_VIDEO_URL`, pre-rotate the file the same way rather than relying on `SPLASH_TRANSFORM_TYPE` — it will silently have no effect on video.
- Passwordless polkit reboot/power-off is deliberately granted to `PI_USER` (see below) — appropriate for a dedicated kiosk device, not for a Pi that's also used as a general multi-user machine.
- **`LED_GPIO_PIN` must be one of GPIO 12, 13, 18, 19, 21, or 10.** These are the only pins on the BCM2711 actually wired in silicon to a PWM/PCM/SPI0 peripheral, which `rpi_ws281x` needs for hardware-DMA-timed output — the same class of approach [WLED](https://kno.wled.ge) itself relies on via ESP32's RMT peripheral (confirmed: WLED explicitly avoids pure software bit-banging for exactly this reason). An earlier version of this build tried driving the strip from GPIO4 via a custom CPU busy-loop bit-bang driver; it produced consistently wrong/flickering colors on real hardware regardless of how the software timing was tuned (three different implementations, including one deliberately 3x slower for more margin, all failed identically) - root-caused to GPIO4 having no such peripheral available at all, not a fixable software bug. If you need a pin outside that set, expect the same limitation.
- **Two strips wired in parallel off one data line mirror each other**, not extend to more unique pixels. The reference build's two 14-LED strips share GPIO21, so `LED_COUNT`/`LED_COUNT_MAX` refer to the 14 *unique* addressable pixels both strips display identically — there's no way to address them independently over a single shared data line without daisy-chaining (strip A's data-out into strip B's data-in) instead of paralleling.
- **Every RetroPie-menu tool actually runs as root**, regardless of whether its `retropiemenu.sh` case entry itself says `sudo`: the custom system's `<command>` wraps the whole dispatch in `sudo openvt ...`, so any child process inherits that. This tripped up the Audio Player specifically — its first version `pip install`ed `python-vlc`/`mutagen` for the calling (non-root) user, which worked when tested directly over SSH as the Pi user but left the packages invisible when actually launched from the menu. Fixed by installing those packages with `sudo pip install` instead. If you add your own tool with pip dependencies, install them the same way.
- **`wpctl` needs the same root-context workaround as the `pip install` gotcha above, for the same reason.** `wpctl` (and PipeWire/WirePlumber generally) talks to the calling user's own session over `$XDG_RUNTIME_DIR` — a tool running as root (see above) has no PipeWire session of its own, so `wpctl get-volume`/`set-volume`/`set-default`/etc. silently fail unless you explicitly point `XDG_RUNTIME_DIR` at the Pi user's runtime dir (`/run/user/<uid>`, found via `os.stat(PI_HOME).st_uid`, not a hardcoded id). The Audio Player, Bluetooth Player, and Audio settings tools all do this via a small `_wpctl_env()` helper — copy that pattern for any tool of your own that shells out to `wpctl`.
- **Debounce confirm/back button presses, not just directional ones.** A physical arcade button or joystick encoder can report more than one rapid press event for what's physically a single tap (contact bounce); for a one-shot action like toggling play/pause or a service on/off, an undebounced double-fire looks to the user like the button "did nothing" (it actually toggled twice) — this is what was actually happening the first time the FTP settings toggle appeared broken. Every RetroPie-menu tool in this project (Audio Player, Bluetooth Player, LED Config, the Bluetooth pairing wizard, Audio settings, WiFi settings, FTP settings) tracks the last confirm/back timestamp and ignores a repeat within 250ms — directional movement is left alone since repeating on a held button is the desired behavior for menu navigation.
- **Bluetooth pairing is fully unattended by design** (this project's own `~/scripts/bt-pairing-agent.py`, registered with `DisplayYesNo` capability, auto-accepts every pairing request with no PIN prompt on either side) — appropriate for a speaker/controller-pairing kiosk, but it does mean anything in Bluetooth range can pair without confirmation. Turn off `ENABLE_BT_SPEAKER` or stop `bt-agent.service` if that's not acceptable for your environment. This replaces `bluez-tools`' own `bt-agent` binary, which — on the BlueZ/D-Bus version this image ships — registered successfully but then hung: its GLib main loop never actually pumped, so it never answered a single pairing confirmation (confirmed live via its own empty journal across several real attempts, and it needed `SIGKILL` on every stop/restart). BlueZ has no fallback for an agent that's registered but unresponsive — it rejects the confirmation in under a millisecond rather than waiting on a dead process, which looked exactly like a rejected pairing to every phone that tried.
- **ES-DE's own Quit-menu Reboot/Power Off actions can silently do nothing.** ES-DE runs `shutdown --reboot now`/`shutdown --poweroff now` internally via a plain C `system()` call whose result it never checks or logs anywhere — if that call doesn't succeed for any reason, the only visible symptom is ES-DE quitting back to the console with the Pi otherwise untouched, since the loop that would normally relaunch it also (correctly) treats this as a deliberate quit and leaves it at the console. ES-DE does unconditionally log "Powering off system"/"Rebooting system" right before that call, though, so `autostart.sh` (step 14) watches for those lines itself and issues the same `shutdown` command directly (verified working under this project's own polkit rule for `PI_USER`) — redundant if ES-DE's own attempt already succeeded, but it's what actually guarantees the menu action happens.
- **The CPU/GPU overclock (`ENABLE_OVERCLOCK`, step 30) is on by default.** An earlier pass through this project's rotation debugging blamed the GPU clock specifically for the rotation bug (see above); re-enabling it after the actual fixes were in place did not reproduce that problem, confirmed live, so it's left on for the performance headroom. It still needs real cooling regardless: `arm_freq=2000`/`gpu_freq=675` are both above stock (1500MHz/500MHz) and were only verified stable on the reference Pi with an active heatsink+fan case — `vcgencmd get_throttled` reads `0x0` (no under-voltage or thermal throttling) on it after these clocks. Lower `OC_ARM_FREQ`/`OC_GPU_FREQ` to something your case can actually sustain under load if unsure; check `vcgencmd measure_temp` and `vcgencmd get_throttled` yourself.
- **PipeWire/WirePlumber's own `bluez5` SPA monitor was unreliable for A2DP on the reference Pi's onboard Bluetooth chip** — confirmed via extensive `btmon` HCI captures and `busctl introspect` inspection of the adapter's registered SDP profiles, which showed endpoints being registered/unregistered per connection attempt instead of staying up. `Device1.ConnectProfile` for the Audio Sink UUID consistently failed as unavailable regardless of role configuration, retries, or connection state, even once a phone was successfully paired. Bluetooth speaker mode (step 25) uses BlueALSA instead for this reason — if you're adapting this project for hardware where PipeWire's own bluez5 monitor works fine, you can drop the WirePlumber override and BlueALSA services and use that instead, but it wasn't reliable enough to ship as the default here.
- **Opening Main Menu > Scraper in ES-DE crashed the whole app instantly, with no error message and no log line at all — this is a real upstream ES-DE 3.4.1 bug, not something wrong with this build's config.** Confirmed via a debug-logged capture: the log shows the Start button press that opens the Main Menu and then nothing else at all before the process exits and the autostart loop (step 14) relaunches it — no kernel-level fault (`dmesg`/`journalctl -k` show nothing either), consistent with an uncaught C++ exception (`std::terminate` → `SIGABRT`) rather than a segfault. Reading the actual `GuiScraperMenu.cpp` source this build compiles found the cause: its constructor loops over every configured system with an index `i` to build the "SCRAPE THESE SYSTEMS" list, skipping any system tagged `platform=ignore` — which this project's own custom "RetroPie Setup" system (step 15) deliberately is, so its ROMs/menu entries never get treated as scrapeable games — but then calls `selectEntry(i)`/`unselectEntry(i)` on that list using the *same* unskipped index `i`, not the position actually reached inside the (shorter) list. The very first system after the ignored one already indexes one past the end — an out-of-bounds access that's unconditionally reached and never caught. Fixed with a source patch (`APPLY_ESDE_SCRAPER_MENU_PATCH`, step 10a) that tracks a separate counter for the real position inside the list.
- **Redream was considered for Dreamcast emulation and rejected in favor of Flycast.** Redream's public GitHub source (`inolen/redream`) only enables its AArch64 JIT backend for Android builds in CMake — its actual Raspberry Pi/"premium" binaries are compiled from a separate, private repo, making it effectively closed-source for this platform — and there's a documented, still-open upstream issue of the official binary failing to even start on 64-bit Raspberry Pi OS with the modern Mesa v3d KMS driver stack this image uses (`sdl initialization failed: No available video device`), a driver-stack match for this exact build. Flycast (`flyinghead/flycast`, GPL2) is fully open source with a genuine ARM64 dynarec and is the standard, well-supported way Dreamcast/Naomi/Atomiswave emulation works on a Pi 4 via RetroPie-Setup, so it's what step 4a actually installs.
- **Flycast has no prebuilt aarch64 package on this OS release, so it's always built from source — which needed two separate fixes for GCC 14.** Debian 13/trixie's default compiler, GCC 14, makes an implicit function declaration (calling a function with no visible prototype in scope — almost always a missing `#include`) a hard compile error by default, where every GCC before it only warned; this is correct-by-default behavior upstream, but it broke building Flycast's bundled `libzip` dependency unchanged for years: `core/deps/libzip/zip_close.c` calls `close()` but only pulled in `<unistd.h>` on `__APPLE__`/`__SWITCH__`, relying on it being available transitively elsewhere on Linux — which silently stopped being true here, confirmed live as the very first build error hit. That one was patched directly (step 3a's companion libzip patch, applied automatically). But a second, different instance of the same class of error turned up on the very next build attempt, in `core/libretro-common/glsm/glsm.c` (`implicit declaration of function 'glBindVertexArray'`) — a GL/GLES symbol-redirection design pattern (`glsym`) where declaring the missing prototype directly would have been the wrong fix, not just a risky one. Rather than patching every individual occurrence of this class of error that a codebase this old and this large might contain, step 3a patches RetroPie-Setup's own compiler-flags setup once, adding `-Wno-error=implicit-function-declaration` project-wide — which is what actually let the Flycast build finish, and benefits any other module built from source afterward too.
- **Dreamcast/Naomi/Atomiswave content needs BIOS files you supply yourself.** `configure_lr-flycast` creates `~/RetroPie/BIOS/dc` for `dc_boot.bin`/`dc_flash.bin` (and, optionally, `naomi.zip`/`awbios.zip` for Naomi/Atomiswave arcade content via Flycast's separate registration under RetroPie's "arcade" system) — these are copyrighted Sega firmware files that must be legally dumped from your own hardware; this project does not provide, link to, or otherwise source them.
- **`bt-power-on.service` failed at every boot** (visible as a "Failed to start bt-power-on.service" line flashed on the console for a moment right before ES-DE launched) — confirmed via `journalctl`: `bluetoothctl power on`/`pairable off` failed with `org.bluez.Error.Busy` every time, because `bt-power-on`, `bt-agent`, and `bt-nowplaying-daemon` all only declared `After=bluetooth.service` and so started in parallel, racing each other's D-Bus calls against the same adapter. Bluetooth itself still ended up working either way (the agent/daemon don't strictly need power-on to have already run), but the failed unit and console flash were real. Fixed by making `bt-agent`/`bt-nowplaying-daemon` also `After=`/`Wants=` `bt-power-on.service`, serializing the three so there's nothing left to race.

## Security notes

- You're piping a script from the internet into `bash`. Review [install.sh](install.sh) before running it, especially if you're adapting it for other hardware.
- The polkit rule this installs (`/etc/polkit-1/rules.d/50-pi-power.rules`) lets `PI_USER` reboot/power off/suspend the system without authentication, so ES-DE/EmulationStation's own quit-menu actions work with no desktop polkit agent running. This is standard for kiosk-style builds but is a real, systemwide privilege change — remove that file if you don't want it.
- The controller hotkey daemon runs as `root` (`/etc/systemd/system/controller-hotkeys.service`), because writing to the backlight's sysfs brightness file needs elevated permission.
